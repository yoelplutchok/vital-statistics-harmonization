# Migration guide: fetal-death v2.0.0 → v2.4.0

> **Scope.** v2.4.0 ships the cumulative result of four data-extension releases over v2.0.0: V2.1 (added 2003-2004 transition years), V3a (added 1989-1991), V3b (added 1982-1988), and the latest-year refresh (added 2023-2024). Plus the v2.0 H8 dtype reconciliation for 5 demographic/filter columns. Coverage extends from 1992-2022 (29 years; 2003-2004 gap) to **1982-2024 (43 contiguous years)**, record count grows from **1,634,195 → 2,427,233**, and the canonical filter behavior is unchanged.
>
> **Audience.** Users with code written against the v2.0.0 Zenodo deposit at [10.5281/zenodo.20031571](https://doi.org/10.5281/zenodo.20031571) who want to upgrade to v2.4.0 in-repo state.
>
> **TL;DR.** No column renames — fetal-death already used the canonical column names (`data_year`, `residence_status`, etc.) at v2.0.0 (natality adopted these at v2.8.0; see [`v2.7.0-to-v2.8.0-natality.md`](v2.7.0-to-v2.8.0-natality.md)). For most analyses, v2.4.0 is a drop-in replacement: just point your code at the new parquet + your existing analytic filter (`tabulation_flag == 2 AND residence_status != 4`) keeps working. The substantive changes are (a) more years to analyze, (b) 5 demographic columns changed from `string` to `int` dtype (some legacy filters comparing to string literals like `"2"` need to compare to int `2` instead), and (c) new era-boundary caveats for V3a + V3b backward years documented inline.

## What changed: a delta-by-delta walkthrough

### Delta 1: v2.0.0 → v2.1.0 (V2.1 transition years 2003 + 2004)

**Coverage**: closes the gap between V2 (1989-revision uniform; 1992-2002) and V1 (2003-revision A/S; 2005+). The 2003-2004 NCHS public-use files use **distinct, non-uniform transition layouts**:
- 2003: 1350-byte records (mixed 1989-revision and 2003-revision content per state's adoption schedule).
- 2004: 1500-byte records (further transition; more states on 2003-revision).
- NCHS published a separate companion document `fetaldeath0304problems.pdf` documenting the layout idiosyncrasies.

**Record-count delta**: +107,782 records (2003: 54,497; 2004: 53,285).

**Bundled H8 dtype reconciliation** ([FIX_LOG 2026-05-11T18:50Z](../FIX_LOG.md) → [FIX_LOG 2026-05-12T01:30Z](../FIX_LOG.md)): five demographic/filter columns were cast from pyarrow `string` to `int` in v2.1:
- `tabulation_flag` (string → int8)
- `residence_status` (string → int8)
- `maternal_age` (string → int8)
- `maternal_race_bridged` (string → int8)
- `hispanic_origin` (string → int8)

**Code-update impact**:

```python
# v2.0.0 code (string-literal filters required)
fd = fd[(fd['tabulation_flag'] == '2') & (fd['residence_status'] != '4')]

# v2.1.0+ code (int filters; v2.0 string filters silently return 0 rows!)
fd = fd[(fd['tabulation_flag'] == 2) & (fd['residence_status'] != 4)]
```

If your v2.0.0 code compares these 5 columns to string literals (`== '2'`), it will silently produce 0 rows when run against v2.1.0+. This is the most common breakage surface; defense pattern is to cast on read or use pyarrow expressions:

```python
import pyarrow.parquet as pq
import pyarrow.compute as pc
import pyarrow as pa

fd = pq.read_table('fetal_death_derived.parquet')
mask = pc.and_(
    pc.equal(fd['tabulation_flag'], pa.scalar(2, type=pa.int8())),
    pc.not_equal(fd['residence_status'], pa.scalar(4, type=pa.int8())),
)
fd = fd.filter(mask)
```

Or in pandas via pre-cast:

```python
fd = pq.read_table('fetal_death_derived.parquet').to_pandas()
for col in ['tabulation_flag', 'residence_status', 'maternal_age', 'maternal_race_bridged', 'hispanic_origin']:
    fd[col] = pd.to_numeric(fd[col], errors='coerce').astype('Int8')
fd = fd[(fd['tabulation_flag'] == 2) & (fd['residence_status'] != 4)]
```

**Validation**: v2.1.0 preserves all 29/29 V2-era NVSR-published per-year counts byte-exact (run `python fetal_death/scripts/05_validate/validate_external_v2.py` to verify).

### Delta 2: v2.1.0 → v2.2.0 (V3a backward extension 1989-1991)

**Coverage**: extends to the 1989-revision uniform era (1989-1991). Same 360-byte record length as 1992-2002 V2 era; harmonization rules from V2 apply unchanged.

**B3 maternal_race_bridged recode** ([DECISION_LOG 2026-05-12T14:30:00Z](../DECISION_LOG.md)): the 1989-revision MRACE field uses 1-digit codes 1-9. Recoding to the 4-category bridged scheme is:
- `1` → 1 (White)
- `2` → 2 (Black)
- `3` → 3 (AIAN)
- `4`-`7`, `8` → 4 (Asian/NHOPI)
- `9` → null (Not stated)

**Caveat**: 09→null affects ~165 records across 1989-1991 (~0.087% per year). Stratified-by-race analyses for V3a era should anticipate this small null fraction.

### Delta 3: v2.2.0 → v2.3.0 (V3b backward extension 1982-1988)

**Coverage**: extends to the 1978-revision uniform era (1982-1988). Much shorter records: **200-byte fixed-width** (versus 360-byte for 1989+ and 1350+/1500+/3050+ for later eras). Fewer fields available; many V2-era columns are blank for V3b years.

**B3 maternal_race_bridged recode** ([DECISION_LOG 2026-05-12T18:30:00Z](../DECISION_LOG.md)): the 1978-revision MRACE field uses 1-digit codes 0-9 (broader code space than 1989-rev):
- `0` → null (Sentinel: unknown)
- `1` → 1 (White)
- `2` → 2 (Black)
- `3` → 3 (AIAN)
- `4`-`5` → 4 (Asian/NHOPI)
- `6`, `8` → 4 (other; older OMB classifications)
- `7` → null (Other nonwhite; no defensible bridged-cat mapping)
- `9` → null (Not stated)

**Caveat**: code 7 → null affects ~89 records total across 1982-1988; code 9 → null affects ~18,700 records (~3-5% per year — substantially higher than V3a's 0.087%). The 1978-revision public-use file has a less-imputed race field than 1989+; researchers using `maternal_race_bridged` to stratify V3b fetal deaths will see totals not exactly add up. The Hispanic_origin column is **null for all V3b years** (1978-revision did not collect Hispanic origin systematically; first introduced in 1989-revision).

**DATAYEAR 2-digit → 4-digit expansion** ([DECISION_LOG 2026-05-12T18:30:00Z](../DECISION_LOG.md), DATAYEAR Option A): the 1978-revision raw layout encodes DATAYEAR as 2 ASCII bytes (e.g., `82` for 1982). Harmonize-layer expands to 4-digit (`1982`) for cross-era consistency. Downstream code should not need to handle the 2-digit form.

**Cross-era race-coding methodology shift** ([C8.10c notebook](../notebooks/cross_race_fetal_mortality.ipynb), 2026-05-13): a downstream consequence of the V3b race-coding history is that pre-2014 cross-era race-stratified panels must use `maternal_race_bridged` on BOTH numerator and denominator sides (bridged 4-cat including Hispanic Whites/Blacks/etc.); 2014+ panels use NH-only bridged 4-cat on both sides (collapsed from `race_hispanic_revised` for fetal-death + `maternal_race_ethnicity_5` for natality). Mixing pre-2014 bridged-incl-Hispanic with 2014+ NH-only-bridged yields artificially deflated 2014+ White FMR. See the C8.10c notebook's Section 3 + the [`docs/COMPARABILITY.md`](../docs/COMPARABILITY.md) cross-product COMPARABILITY synthesis for the bilateral methodology.

### Delta 4: v2.3.0 → v2.4.0 (latest-year refresh 2023 + 2024)

**Coverage**: extends to current. 2023 + 2024 use the same 1989-revision-derived layout as 2018-2022 (`Fetal<YYYY>US_COD.zip`; 2652-byte records; COD-only variant).

**No methodology changes**; this is a pure data-extension. Existing 2014+ analytic code works unchanged against 2023+2024 records.

**Record-count delta**: +75,222 records (2023: 39,574; 2024: 35,648).

**NCHS documentation reorganization caveat**: the doc URL pattern changed for 2023+ — NCHS now serves the user guides at `https://ftp.cdc.gov/pub/Health_Statistics/NCHS/Dataset_Documentation/DVS/fetaldeath/` (note: `fetaldeath` without the `us` suffix). The data zips themselves remain at `https://ftp.cdc.gov/pub/Health_Statistics/NCHS/Datasets/DVS/fetaldeathus/`. See [`fetal_death/file_inventory.csv`](../fetal_death/file_inventory.csv) 2023+2024 rows for the exact URLs.

## Remaining latent state at v2.4.0: ~50 string-typed columns

[FIX_LOG 2026-05-12T22:00:00Z](../FIX_LOG.md) (the C8.1 dtype-parity audit) found that ~50 fetal-death raw harmonized columns still ship as pyarrow `string` despite `harmonized_schema.csv` declaring them as `int` or `float`. Affected columns include: `delivery_year`, `maternal_age_recode14/9`, `maternal_race_multi`, `maternal_race_recode6`, `maternal_race_bridged_detail`, `race_hispanic_combined`, `race_hispanic_revised`, `maternal_education(_unrevised)`, `marital_status`, `maternal_nativity`, `paternal_age_combined`, `paternal_age_recode11`, `live_birth_order`, `plurality`, `prenatal_care_*`, `delivery_method_*`, `delivery_route`, `prior_cesarean_number`, `gestational_age_clinical/oe_edited/combined`, `gestational_age_recode12/5`, `oe_gest_recode12/5`, `birthweight`, `birthweight_recode14/4`, `fetal_presentation`, `diabetes_unrevised`, `chronic_hypertension_unrevised`, `pregnancy_hypertension_unrevised`, `eclampsia_unrevised`, `tobacco_*`, `prepregnancy_bmi(_recode)`, `cause_recode124`, `cause_reporting_flag`, `attendant`, `delivery_place_*`, `breech_unrevised`, `gestation_imputed_flag`, `obgest_used_flag`.

The C8.1 test `fetal_death/tests/test_schema_dtype_parity.py::test_full_schema_type_matches_parquet_dtype` is `@pytest.mark.xfail(strict=True)` and PASSes (returns XFAIL); a future task is required to either cast the columns to their declared dtypes in `harmonize.py` (recommended) OR rephrase the schema CSV's `type` column to declare `str` for these columns (lower-cost alternative).

For most analytic uses these columns ship as **fixed-width string codes** that map to documented value-spaces (e.g., `'01'` through `'08'` for `maternal_education`); your existing code probably treats them as categorical strings already. If a query is filtering or aggregating on one of these columns and your v2.0 code used `.astype(int)` or numeric comparisons, you may want to add a `pd.to_numeric(..., errors='coerce')` cast on read.

## Path 1: Drop-in replacement (most code)

```python
import pyarrow.parquet as pq

# v2.0.0
fd_v20 = pq.read_table('fetal_death_derived.parquet')  # 1,634,195 rows × 89 cols
# v2.4.0
fd_v24 = pq.read_table('fetal_death_derived.parquet')  # 2,427,233 rows × 89 cols

# Canonical analytic filter is unchanged
mask_v20 = (fd_v20['tabulation_flag'] == '2') & (fd_v20['residence_status'] != '4')  # v2.0 string-literal
mask_v24 = (fd_v24['tabulation_flag'] == 2)   & (fd_v24['residence_status'] != 4)    # v2.4 int
```

For most queries: just point your code at the new parquet, **convert string-literal comparisons to int** for the 5 H8-reconciled columns, and you're done.

## Path 2: Year-window scoping

If you're not ready to consume the V3a + V3b backward years (e.g., your existing analysis is scoped 1992-2022), restrict by `data_year`:

```python
# Replicate v2.0.0 envelope from v2.4.0
fd_v20_subset = fd_v24[(fd_v24['data_year'] >= 1992) & (fd_v24['data_year'] <= 2002) |
                       (fd_v24['data_year'] >= 2005) & (fd_v24['data_year'] <= 2022)]
# Note: this OMITs 2003-2004 (v2.1 transition) which v2.0.0 didn't have
# Adjust as needed if you want the v2.1.0 envelope (1992-2022 contiguous):
fd_v21_envelope = fd_v24[(fd_v24['data_year'] >= 1992) & (fd_v24['data_year'] <= 2022)]
```

## What did NOT change

- Column count: 89 columns in `fetal_death_derived.parquet` (73 harmonized + 16 derived); unchanged across all versions.
- Schema column ORDER: stable across versions.
- Canonical analytic filter: `tabulation_flag == 2 AND residence_status != 4` (NVSR-published-aggregate equivalent) unchanged.
- Era nomenclature: V1 = 2005-2017 (transition); V2 = 1992-2002 (1989-rev uniform); V2.1 = 2003-2004 (mixed transition); V3a = 1989-1991 (1989-rev uniform); V3b = 1982-1988 (1978-rev uniform). All preserved.
- Joint-use convenience layer: `stratified_denominators.csv` still ships at the fetal_death/ root.
- Zenodo concept DOI: [10.5281/zenodo.20031571](https://doi.org/10.5281/zenodo.20031571) unchanged; v2.0.0 deposit at [10.5281/zenodo.20031571](https://doi.org/10.5281/zenodo.20031571) (v2.0.0) immutable.
