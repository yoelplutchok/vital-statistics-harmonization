# Migration guide: natality v2.7.0 → v2.8.0

> **Scope.** v2.8.0 introduces a **canonical column-name rename** across 4 fields to align natality's column names with the fetal-death subproject's harmonized schema. The data values are unchanged; this is a column-renaming migration, not a re-derivation.
>
> **Audience.** Users with code written against natality v2.7.0 (the canonical Zenodo deposit at [10.5281/zenodo.19868835](https://doi.org/10.5281/zenodo.19868835)) who want to upgrade to v2.8.0 in-repo state OR who want to write version-agnostic code that works against either deposit.
>
> **TL;DR.** Use `shared/helpers/canonical_join_keys.py::to_canonical_natality()` for the cheapest migration path. The helper accepts both v2.7.0 and v2.8.0 dataframes + returns the v2.8.0-canonical columns either way (no-op on v2.8.0 input; full rename on v2.7.0 input). Backward-compat preserved indefinitely.

## What changed

Four column renames; nothing else:

| v2.7.0 column | v2.8.0 column | Type | Notes |
|---|---|---|---|
| `year` | `data_year` | int16 | Now matches fetal-death subproject's `data_year` |
| `restatus` | `residence_status` | int8 | Now matches fetal-death's `residence_status`; canonical filter `residence_status != 4` (foreign residents) unchanged |
| `maternal_race_bridged4` | `maternal_race_bridged` | int8 | Now matches fetal-death's `maternal_race_bridged`; 4-category bridged race classification unchanged (`1=White, 2=Black, 3=AIAN, 4=Asian/NHOPI`); null pre-1990 + 2018+ unchanged |
| `maternal_hispanic_origin` | `hispanic_origin` | int8 | Now matches fetal-death's `hispanic_origin`; codes 0-5 + 9 unchanged |

**What's NOT changed**: parquet partitioning, row count (138,819,655), other 80 columns, validation cells (183/183 NVSR targets still byte-exact under v2.8.0), Zenodo concept DOI ([10.5281/zenodo.19363074](https://doi.org/10.5281/zenodo.19363074)). The v2.7.0 deposit at [10.5281/zenodo.19868835](https://doi.org/10.5281/zenodo.19868835) is immutable and remains the canonical citable artifact until the unified-HVS Zenodo deposit (planned).

## Why this changed

Cross-product joint-use code (computing fetal mortality rate using both natality denominators + fetal-death numerators per [`docs/JOINT_USE_GUIDE.md`](../docs/JOINT_USE_GUIDE.md)) required either (a) renaming columns on every read or (b) maintaining a parallel column-name dictionary. The v2.8 rename adopts the fetal-death subproject's naming convention as the canonical, eliminating ~61 rename string literals across the joint-use codebase ([`DECISION_LOG.md` 2026-05-12T03:25Z](../DECISION_LOG.md)).

## Path 1: Use the version-agnostic helper (recommended)

The `shared/helpers/canonical_join_keys.py::to_canonical_natality()` wrapper works for both v2.7.0 and v2.8.0 input. It renames only the columns that exist in the input + skips the rest, so it is a no-op on already-canonical v2.8.0 dataframes.

```python
from shared.helpers.canonical_join_keys import to_canonical_natality
import pyarrow.parquet as pq

# v2.7.0 path (old column names)
nat_v27 = pq.read_table('natality_v2_harmonized_derived.parquet').to_pandas()
nat = to_canonical_natality(nat_v27)
# nat now has 'data_year', 'residence_status', 'maternal_race_bridged', 'hispanic_origin'

# v2.8.0 path (already canonical)
nat_v28 = pq.read_table('natality_v2_harmonized_derived.parquet').to_pandas()
nat = to_canonical_natality(nat_v28)
# nat unchanged (helper is a no-op when input already has canonical names)
```

Same wrapper works regardless of which Zenodo deposit you loaded from. This is the recommended pattern for code that should outlive multiple natality version bumps; see [`DECISION_LOG.md` 2026-05-12T13:35:02Z](../DECISION_LOG.md) for the retention rationale.

## Path 2: Direct rename in pandas (for one-off scripts)

```python
import pandas as pd
import pyarrow.parquet as pq

nat = pq.read_table('natality_v2_harmonized_derived.parquet').to_pandas()
nat = nat.rename(columns={
    'year':                       'data_year',
    'restatus':                   'residence_status',
    'maternal_race_bridged4':     'maternal_race_bridged',
    'maternal_hispanic_origin':   'hispanic_origin',
})
```

If your code is loading the v2.7.0 deposit directly (e.g., from a frozen analysis pipeline), apply this rename right after loading. If you're loading v2.8.0, this rename is a no-op (the columns will be renamed-to-themselves).

## Path 3: pyarrow column projection at load time

For users who want to skip loading the renamed columns entirely (memory-efficient for large queries):

```python
import pyarrow.parquet as pq

# v2.7.0: project + rename
desired_old = ['year', 'restatus', 'maternal_race_bridged4', 'hispanic_origin']
nat_v27 = pq.read_table('natality_v2.7.0.parquet', columns=desired_old)
nat_v27 = nat_v27.rename_columns(['data_year', 'residence_status', 'maternal_race_bridged', 'hispanic_origin'])

# v2.8.0: project directly with new names
desired_new = ['data_year', 'residence_status', 'maternal_race_bridged', 'hispanic_origin']
nat_v28 = pq.read_table('natality_v2.8.0.parquet', columns=desired_new)
```

## Path 5: DuckDB views

The `views.sql` file (shipped at C8.9; loaded into a DuckDB session via `.read views.sql`) provides version-agnostic views over the natality parquet. The view `natality_canonical` always exposes the v2.8.0 column names, applying renames if necessary:

```sql
-- views.sql (excerpt)
CREATE VIEW IF NOT EXISTS natality_canonical AS
SELECT
  COALESCE(data_year, year)                                      AS data_year,
  COALESCE(residence_status, restatus)                           AS residence_status,
  COALESCE(maternal_race_bridged, maternal_race_bridged4)        AS maternal_race_bridged,
  COALESCE(hispanic_origin, maternal_hispanic_origin)            AS hispanic_origin,
  -- (other 80 columns passed through unchanged)
  ...
FROM read_parquet('natality_v2_harmonized_derived.parquet');
```

Then downstream queries `SELECT * FROM natality_canonical WHERE data_year = 2022 AND residence_status != 4 ...` work against either version's underlying parquet. The full DDL ships at [`views.sql`](../views.sql).

## sed/awk recipes for code-update sweeps

If you have a large codebase referencing the v2.7.0 column names in source files, the following recipes apply the rename surgically. Use with `git status` after each pass + spot-check the diff.

### Bash + GNU sed (in-place):
```bash
# WARNING: makes in-place edits; commit your tree first.
find . -type f \( -name '*.py' -o -name '*.R' -o -name '*.sql' -o -name '*.ipynb' \) \
  -not -path '*/\.git/*' \
  -exec sed -i \
    -e 's/\byear\b/data_year/g' \
    -e 's/\brestatus\b/residence_status/g' \
    -e 's/\bmaternal_race_bridged4\b/maternal_race_bridged/g' \
    -e 's/\bmaternal_hispanic_origin\b/hispanic_origin/g' \
    {} +
```

**WARNING — `year` rename is risky in bulk.** The bare word `year` may match unrelated variable names (`birth_year`, `paper.year`, etc.). Inspect each match before committing. The fetal-death subproject's `data_year` column has the SAME name in both v2.0.0 and v2.4.0 — confirming the rename is naturally cross-product-consistent at v2.8.0 — but in your own code, `year` as a local variable name is unaffected by NCHS's column rename.

Recommended safer pattern: search-replace ONE column at a time, inspect diff, commit.

### macOS sed (BSD; requires backup-suffix argument):
```bash
# macOS BSD sed; backs up to .bak; review + delete after commit
find . -type f \( -name '*.py' -o -name '*.R' -o -name '*.sql' \) \
  -not -path '*/\.git/*' \
  -exec sed -i '.bak' \
    -e 's/maternal_race_bridged4/maternal_race_bridged/g' \
    -e 's/maternal_hispanic_origin/hispanic_origin/g' \
    -e 's/\brestatus\b/residence_status/g' \
    {} +
# After verifying: find . -name '*.bak' -delete
```

### Python-script-based (most controllable):
```python
# rename_v27_to_v28.py — surgical, with logging
import re, pathlib
RENAMES = [
    (r'\bmaternal_race_bridged4\b', 'maternal_race_bridged'),
    (r'\bmaternal_hispanic_origin\b', 'hispanic_origin'),
    (r'\brestatus\b', 'residence_status'),
    # 'year' rename intentionally OMITTED — too noisy; do manually
]
ROOT = pathlib.Path('.')
for f in ROOT.rglob('*'):
    if '.git' in f.parts or f.suffix not in ('.py', '.R', '.sql', '.ipynb'):
        continue
    src = f.read_text()
    new = src
    for pat, repl in RENAMES:
        new = re.sub(pat, repl, new)
    if new != src:
        print(f'{f}: {sum(1 for p,_ in RENAMES if re.search(p, src))} renames')
        f.write_text(new)
```

The `year` column rename is intentionally manual — see warning above.

## Backward compatibility

- **v2.7.0 Zenodo deposit ([10.5281/zenodo.19868835](https://doi.org/10.5281/zenodo.19868835))** is immutable. The deposit's column names are the v2.7.0 names; this will never change.
- **v2.8.0 in-repo state** (this repository's current natality parquets) uses the new canonical column names. Until the unified-HVS Zenodo deposit lands (Phase D step 2 of the pre-submission plan), the v2.7.0 deposit remains the canonical citable artifact.
- **The aliasing helper** is retained indefinitely in `shared/helpers/canonical_join_keys.py` so that joint-use code can transparently consume either deposit. See [`DECISION_LOG.md` 2026-05-12T13:35:02Z](../DECISION_LOG.md) for the retention rationale.

## Validation

After applying the migration to your code, run any existing query / notebook against both v2.7.0 and v2.8.0 parquets — under the helper, results should be byte-identical for all 183 NVSR validation cells. The natality_v28_rename receipt at commit `a6b3d36` records the cross-version validation done in-repo: `notebooks/paper_companion_results.csv` is byte-identical at sha=`7891809c…` whether built against v2.7.0 or v2.8.0 input parquets.
