### Self-check (per NEXT_STEPS.md §10)

What could I have gotten wrong that VERIFY wouldn't catch?

1. **Per-year canonical-filter count VERIFY uses int literals (`tabulation_flag==2`)**, which only works because of the C8.1 / V2.1 H8 fix that cast these columns to int. If a future canonical-state mutation re-introduces string typing for these columns, the C8.2 VERIFY check would silently break (no records would match `==2`). Mitigation: `test_v21_h8_fixed_columns_remain_int` smoke test (5 columns, strict int) is part of every CI run. If that regresses, this VERIFY breaks the same way and is caught by smoke.

2. **NVSR Table 8 cause-of-death cells were NOT re-validated for 2023+2024** because NVSR 73-09 / 74-XX for these years isn't published yet. The 2023+2024 COD column shipped in the parquet (via the COD bytes in the FETAL_2018_2022_FIELDS layout that explicitly include F_ICOD etc.) is parsed correctly per the byte-position diff but is NOT externally validated until NVSR publishes per-year COD tables. A latent ICD-10 coding revision between 2022 and 2024 would not be caught by C8.2 VERIFY. Mitigation: documented as forward-looking soft-flag; future Phase C task (post-NVSR-74 publication) can validate the new years' COD cells.

3. **The page-count difference (2022: 80 → 2024: 86)** was noted but not investigated — NCHS may have added new layout fields beyond the regex-captured 17 (start,end,field) triples I checked. If NCHS added new fields between 2022 and 2024 (e.g., at unused trailing bytes 2652+ of the layout) and they're documented in the new pages, my parser silently ignores them and downstream users analyzing 2023+2024 records would miss the new field. Mitigation: my parser only reads 2651 bytes; any new layout fields beyond byte 2651 would be in the trailing FILLER region and remain trailing FILLER. Unless NCHS expanded the record length (which I verified is still 2651), no new fields are present. The page-count growth is more likely cosmetic (NCHS adding new tables of summary statistics like the page 60-62 tables, not new layout fields).

4. **The B7 TABFLG correction for 2003-2004 is era=='2003' only**; 2023 and 2024 use era=='2022' which doesn't apply B7. If NCHS changed TABFLG semantics between 2022 and 2024, the canonical filter `tabulation_flag==2` would silently return wrong records. My VERIFY confirms the canonical-filter count matches the user-guide control count byte-exact, which would catch any TABFLG semantic shift — so this risk is actually well-defended.

5. **Smoke test 7 (`test_per_year_row_counts_within_5pct`)** uses ±5% threshold; the 2023+2024 entries I added to `EXPECTED_YEAR_ROWS` are pinned exact values that came from this very session's parse. A future re-parse with a different parser version would either match exactly (good) or drift within the 5% threshold (would still pass without surfacing the issue). Mitigation: the parser SHA is recorded in this receipt; a parser change that affects record counts would trigger a non-trivial diff visible at `git diff fetal_death/scripts/01_import/parse_fetal_year.py`.

6. **The 4× `__init__.py` files** (from C8.1-followup commit) may interact in unexpected ways with future package-management work at C8.5 (lockfile + pyproject.toml). The subprojects are now formal Python namespaces (`fetal_death`, `natality`) — if C8.5 tries to `pip install` them as packages, the empty `__init__.py` will be picked up. Currently they're inert; future risk surfaced as forward-looking soft-flag in DECISION_LOG 22:30Z residual risk (b).

7. **User-guide URL pattern changed** between 2022 (`Dataset_Documentation/DVS/fetaldeathus/`) and 2023+ (`Dataset_Documentation/DVS/fetaldeath/`). I documented this in file_inventory.csv notes for 2023+2024 rows, but did NOT retroactively update the 2003-2022 rows' notes. If NCHS later sunsets the `fetaldeathus/` directory entirely (already deprecated for docs), the 2003-2022 user-guide-URL implicit assumption breaks. Mitigation: the existing 2003-2022 user-guide files are on disk; the URL in file_inventory.csv `source_url` is for the zip (still valid at `fetaldeathus/`); only the doc subpath shifted. Risk is minimal; no action needed unless a future doc re-fetch fails.
