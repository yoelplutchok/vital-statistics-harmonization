### Self-check

What could I have gotten wrong that VERIFY wouldn't catch?

1. **The xfail(strict=True) gate may rot silently.** If a future task happens to align all schema 'int' rows to parquet int dtypes (e.g., as a side effect of dictionary tuning or a casting bug), the xfail flips to XPASS=FAIL and the future LLM may incorrectly "fix" the test by removing the xfail without first verifying the reconciliation is intentional. Mitigation: the xfail docstring explicitly names the closure conditions ("future task casts more columns to int OR rephrases schema type column to declare 'str'") and points at the FIX_LOG entry being filed alongside this receipt.

2. **`_regenerate_schema_years.py` monorepo copy could drift from the standalone-build source.** I made path-adapted edits to module-level constants but did not bind the two copies via symlink or shared import. A future change to the standalone-build version (e.g., adding a new column-type heuristic) would not propagate. Mitigation: documented in the copied file's header that it is the "monorepo-adapted sibling" of the standalone version. A future C8.X task could DRY this up (e.g., move to `shared/helpers/`).

3. **The new fetal_death dtype parity test interprets `type='int'` as "any pyarrow int width acceptable", but the schema's `int32` (1 row) is treated strictly.** If a future task reclassifies that int32 column as plain `int`, the test would accept any int width — losing the int32 specificity. Mitigation: the int32 distinction is preserved in `_SCHEMA_TYPE_ACCEPTABLE`; a future schema rename would surface in `test_schema_csv_matches_harmonized_columns` (set equality test 2).

4. **The natality dtype parity test loads two large parquets (138.8M + 74.9M rows).** Each fixture is session-scoped so the load only happens once per pytest invocation, but CI runtime is sensitive to this. For B.9 (CI wiring, C8.6) I should consider parametrizing the natality test to load a sample or shape-only metadata. The current test only inspects schema (pyarrow `schema_arrow`), which is O(1) per parquet; row counts are not touched. Verified: pytest natality/ runs in <0.2 sec total.

5. **The schema regen mutates a versioned artifact.** Per Anti-Pattern #6, schema edits require version bump OR DECISION_LOG entry. I'm filing the DECISION_LOG entry alongside this receipt; the schema-version bump is deferred because `years_available` is auto-derived (not a hand-authored decision) and the regen script's purpose is exactly this. The DECISION_LOG entry documents the reasoning.
