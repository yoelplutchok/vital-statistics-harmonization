### Self-check

**What could I have gotten wrong that VERIFY wouldn't catch?**

1. **Hybrid schema naming choices may not survive cross-product joinability scrutiny.** The 4 cross-product analog columns (`maternal_age`, `maternal_race_hispanic`, `maternal_education_cat4`, `sex_infant`) align in NAME with the fetal_death + natality siblings but the WITHIN-ERA collapse rule for `maternal_race_hispanic` differs subtly from how fetal_death + natality encode the same concept (1995-X uses ORRACEM 4-cat; 2016-2020 collapses MRACEHISP 8-cat → 4-cat). A naive cross-product join on `maternal_race_hispanic` will produce semantically-misleading rates because the 2016-2020 `NH_Other` category includes AIAN + Asian + NHOPI + multiple-race rows that the 1995-X residual `NH_Other` does not. The notebook Section 5 documents this, but a user copy-pasting the joint-use guide pattern might miss it. **Mitigation:** the schema row's `comparability_class=within_era` flags this, and the notebook commentary is explicit. If a user fails to read either, this could surface as a residual diff at cross-product validation time.
2. **The 1995-2000 file is NOT a strict supersession of 1995-1997.** Both files cover overlapping years (1995-1997) with different matching methodologies. A user concatenating both files would double-count those years; a user choosing the wrong file for 1995-1997 analysis would get the wrong methodology generation. The harmonized parquet enforces `data_window` as a partitioning column to disambiguate, but if a user filters only on `data_year` (window-implicit for 1995-X) and aggregates across windows, double-counting is possible. **Mitigation:** ABOUT_SOURCE_DATA.md "Methodology differences" section + notebook Section 5 documents the non-supersession explicitly.
3. **`cause_of_death_icd_revision` for 1995-2000 was derived by picking the non-blank UCOD9 vs UCOD10 block.** The cross-tab in the notebook section 4 shows 1995-2000 splits 14,504 ICD-9 + 7,715 ICD-10 (total 22,219 infant deaths). The 1999 ICD-revision boundary in the U.S. mortality file series is well-established, but my derivation rule (whichever block is non-blank wins) could over/under-attribute if the source file has ANY records with BOTH blocks populated (which would be a bug in NCHS's data). I assumed the blocks are mutually exclusive per record; if not, my UCOD10-priority rule (`u10.where(u10.notna(), u9)`) would silently shadow ICD-9 codes. **Mitigation:** could be validated by counting records with both blocks non-blank; for now, the 14,504 + 7,715 = 22,219 = total infant_death count is a strong sanity check (no double-counting; no missing).
4. **The variable-length 2016-2020 right-pad to 157 bytes** in the parser handles the trailing-UCODR130-blank-strip case, but the parser would NOT detect a record where the trailing bytes contain partial UCODR130 data + an OS-line-ending artifact that some downstream user might re-introduce. Empirical row count 641,934 matches PDF Table 1 byte-exact, which is the strongest available sanity check.
5. **The notebook prose-level IMR cross-validation (10.14/1,000) for complete twin sets** uses the PDF text-extracted prose passage which had column-header transcription noise from PyMuPDF's text-layer. The notebook documents this and uses the 10.14 figure (which is byte-exact reproducible from `set_complete ∈ {1, 2}` ∧ `set_size = 2`) rather than the prose's 10.82 (which references "complete + incomplete" under a denominator definition the text extraction obscured). If a future audit re-reads the PDF via a different extraction tool and finds the 10.82 figure has a clear unambiguous definition, my notebook may need a follow-up extension to also verify that cell. For now, the byte-exact 10.14 reproduction is the analytic-fidelity backbone.
6. **`tests/test_source_zip_sha_stability.py::test_source_zip_sha_matches_manifest`** verified the 3 matched-multiples zip SHAs against the manifest, but it reads them from `/tmp/c8_16_zip_probe/` which is OS-cleanable. If `/tmp` is cleaned between this RECEIPT and a future test run, the matched-multiples branch of that test will skip (zips missing) while the fetal-death + natality + linked branches continue to verify. **Mitigation:** a future C8.X may promote the matched-multiples zips to a canonical `raw_data/matched_multiples/` location (sibling of `raw_data/fetal_death/`), per the soft-flag carried in STATUS.
