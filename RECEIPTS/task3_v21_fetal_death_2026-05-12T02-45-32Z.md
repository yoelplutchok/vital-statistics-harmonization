### Self-check

What could I have gotten wrong that VERIFY wouldn't catch?

1. **V1-era column-level byte-clean regression not exhaustively verified.** The V1 validator passed 55/55 (functional), but a column-by-column SHA-256 of the 2005–2022 slice of the new `fetal_death_derived.parquet` was NOT compared cell-by-cell against v2.0.0's `90af89b9…` baseline. The 5 H8 columns are expected to differ (string→Int); the other 84 columns SHOULD be byte-identical but I did not prove it cell-by-cell. Forward-looking HALT 1 below schedules this check.

2. **The B7 OSTATE-vs-XOSTATE equivalence argument.** The 43-state list contains neither `NY` nor `YC`, so OSTATE (@30-31) and XOSTATE (@32-33) yield the same result for B7 matching. Verified by direct byte-read of the raw 2003 file (42,322 of 54,497 records have OSTATE==XOSTATE; the 12,175 differences are NYC records where OSTATE='NY' and XOSTATE='YC'). The argument is sound but rests on the 43-state list being correct (43 codes, verified) AND the parser reading bytes 30-31 correctly AND the underlying 2003-file convention being stable.

3. **`maternal_age=null` for 2003+2004 may surprise users.** The V2_1_DECISIONS doc documents this; the JOINT_USE_GUIDE dtype note mentions it; downstream code that joins on `maternal_age` for 2003+2004 will silently produce zero matches. Mitigation: documentation; could add a warning at quickstart.py load time but did not.

4. **Other monorepo scripts with similar path drift.** Three were fixed (harmonize.py, validate_external.py, validate_external_v2.py); `parse_fetal_year.py`, `derive.py`, `run_pipeline.py`, `tests/conftest.py` were NOT inspected for path drift. The end-to-end `run_pipeline.py` smoke from the monorepo root has not been verified. Forward-looking HALT 5.

5. **The 2003+2004 yearly_clean parquet's column named `MAGER` actually contains `MAGER41` codes.** The yearly_clean parquet is documentation-imprecise; harmonize-time omission of `maternal_age` from the era="2003" mirror produces correct harmonized output. But if any downstream code reads the yearly_clean parquet directly and treats `MAGER` as single-year-of-age for 2003+2004, it would silently produce wrong analyses. Mitigation: harmonized output is the canonical artifact, not yearly_clean. Documented in V2_1_DECISIONS.

6. **MAGER41 → MAGER14 might fail to bridge cleanly for cross-era analyses.** For age-stratified analyses spanning 1992–2022, users now have: 1992–2002 single-year `maternal_age`; 2003–2004 null `maternal_age` + 14-cat `maternal_age_recode14`; 2005–2022 single-year `maternal_age` (boundary-coded 12–50). The aggregated 14-cat bins for 2003/2004 (from MAGER14 codes) should align with the single-year `maternal_age` bins for the other years if a researcher computes `maternal_age_band` from single-year. Did not exhaustively verify alignment of the V1-era MAGER14 14-cat coding with the V2/V2.1 maternal_age binning — possible source of cross-era discontinuity.

7. **`data_year` int32 fix is forward-correct but past-state-traced incomplete.** I do not have a clean explanation for how v2.0.0 produced int32 `data_year` despite the same bug being latent in harmonize.py. Either v2.0.0 ran a different code path (perhaps `--sentinels` mode was on by default in the pre-Task-3 era and `_apply_sentinels` repaired the dtype as a side effect), or v2.0.0's validator passed despite a different `data_year` dtype. Not traced; v2.1.0 ships with int32 `data_year` matching v2.0.0 functional behavior. The fix is forward-compatible.
