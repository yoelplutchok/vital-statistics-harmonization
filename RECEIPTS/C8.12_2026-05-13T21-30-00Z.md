### Self-check (per §10 — "what could I have gotten wrong that VERIFY wouldn't catch?")

1. **The B.6 mutation tests assert STRUCTURAL invariants (non-zero exit + FAIL surface), not the specific FAIL semantics.** A future validator regression that exits non-zero AND prints "FAIL" for an UNRELATED reason (e.g., crashes on a corrupted parquet before reaching the per-row check) would still PASS the mutation test as currently written. Defense: the assertion is intentionally Convention 1 SHAPE-not-VALUE per §4.2.1; pinning specific FAIL-message wording would convert this to a fragile L17-class stale pinning. Trade-off accepted: structural invariants survive validator-output-message rewording at the cost of some false-positive-PASS risk. Mitigation via the AND-of-rows aggregation: both non-zero exit AND a recognizable FAIL marker must hold; a crash without "FAIL" in output fails the second condition.
2. **The `test_validate_linked_parquets_mutation` test SKIPs on this build** because `natality/output/linked/` is absent. I authored the mutation logic + assertion but did NOT verify it triggers FAIL via end-to-end execution on a real linked-parquet input. Risk: the `_zip_implied_rows` lambda-wrap may not trigger the validator's "Row count mismatch" branch as intended (the validator's logic may have edge cases I haven't probed). Defense: the harness pattern is identical to the 6 passing tests; the mutation is a 1-line lambda over a single function `_zip_implied_rows` with a clear return-value contract (int or None). Manual verification deferred to the build session where `natality/output/linked/` becomes available (likely Phase D step 3 first CI sync, or when C8.7b orchestrator authors the symlink). Filed as soft-flag (n) below.
3. **The `test_validate_v1_invariants_mutation` exercises the validator's UPFRONT precondition path (line 114-141 RuntimeError on missing required column), NOT the deep invariant-scan FAIL surface (line 884 `SystemExit(2)` after 138M-row scan).** Choosing the precondition path was a deliberate speed/coverage trade-off (<5s vs ~60-120s) per the receipt's explanatory docstring. Risk: the deep-scan FAIL surface (the validator's actual reason for existing) is not mutation-tested. Defense: the precondition check IS a load-bearing fail-closed defense; the validator's downstream invariant logic IS exercised in production runs (when the user runs the validator against the real parquet). A future C8.X could add a second-tier mutation test that does mutate the deep-scan path (e.g., by patching `_count_true` to return a positive int, forcing every violation counter into "exceeds budget" state).
