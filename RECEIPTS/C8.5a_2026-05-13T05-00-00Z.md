### Self-check

What could I have gotten wrong that VERIFY wouldn't catch?

1. **The `uv.lock` was generated on macOS arm64 (Darwin 21.6.0, miniconda).** Some packages have platform-specific wheels (e.g., pyarrow has separate wheels for macos-arm64, macos-x86_64, linux-x86_64, manylinux2014_x86_64, win-amd64). The lockfile resolves to a set of wheels including platform-specific variants — but uv's lockfile is intended to be cross-platform and includes resolution metadata for all supported platforms. A future `uv sync` on a Linux x86_64 machine (e.g., GitHub Actions ubuntu-latest) will pick the Linux wheel for the same pinned version. Mitigation: C8.6 CI will validate this on the GitHub Actions runner, surfacing any cross-platform lockfile defects. If GitHub Actions surfaces a "no wheel for platform" error, the lockfile may need a re-lock with explicit `--platform` extension.

2. **The `requires-python = ">=3.13,<3.14"` is narrow.** A user on Python 3.12 cannot `uv sync` against this lockfile; a user on 3.14 (when released) cannot either. This is intentional — matches build env — but documented users may be surprised. Mitigation: README section explicitly cites Python 3.13. Future Python-version-bump can be authorized via §11 plan-update.

3. **`jupyter` was dropped vs `requirements.txt`'s declared `jupyter>=1.0`.** PRE-FLIGHT discovered the metapackage was NOT actually installed (`pip show jupyter` → not found; `import jupyter` → no `__version__`); only `nbformat` + `nbclient` + `jupyter_core` are in the build env. The lockfile reflects build-env reality, not requirements.txt declaration. End-users who want full jupyter interactive notebook running may need to install `jupyter` separately (`uv pip install jupyter`). Mitigation: README section + C8.5 §15 DO scope note. A future PRE-FLIGHT may reconcile requirements.txt with the lockfile (drop `jupyter>=1.0` from requirements.txt, add `nbformat` + `nbclient` explicitly).

4. **`requests` 2.32.5 is installed but not pinned in the lockfile.** PRE-FLIGHT found `requests` installed in the build env but no `import requests` in any tracked file. It's probably pulled in transitively by a tool not in the lockfile (e.g., the WebFetch path). The lockfile correctly omits it. If a future task adds `import requests` to a tracked file, that task's PRE-FLIGHT must add `requests` to `pyproject.toml`.

5. **The `.venv` created by `uv sync` lives at `.venv/` (gitignored) and is ~hundreds of MB.** A future C8.5b Dockerfile must NOT bake `.venv/` into the image; it must run `uv sync` inside the build stage. The `.dockerignore` (C8.5b deliverable) must explicitly exclude `.venv/`.

6. **`uv` 0.11.10 is a recent uv version.** A user on an older uv (e.g., 0.4.x without `[dependency-groups]` support) may fail to `uv sync`. Mitigation: lockfile format is mostly backward-compatible; the `[dependency-groups] dev` table syntax is PEP 735 (December 2024+). Documented uv version requirement could be added to README — soft-flag for future polish.

7. **pytest auto-discovered `pyproject.toml` as its config root.** This may change pytest's collection behavior vs the prior in-the-subproject discovery. In this run, 57 items collected (same as C8.4-complete), so no observable regression — but a future test addition that depends on a per-subproject conftest discovery path could surface a difference. Mitigation: the `pyproject.toml` we authored does NOT include a `[tool.pytest.ini_options]` block; pytest's discovery falls back to its default (which produced the correct collection here).

(See `NEXT_STEPS.md` §8 mistake-class matrix; closest classes: H10 reproducibility drift, L13 inventory-vs-content mismatch — both defended by the lockfile mechanism itself, but cross-platform lockfile defects are a new variant not directly in the matrix.)
