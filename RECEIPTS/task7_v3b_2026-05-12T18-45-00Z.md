### Self-check (NEXT_STEPS §10)

**What could I have gotten wrong that VERIFY wouldn't catch?**

1. **V3a/V2/V2.1/V1 byte-clean was checked column-by-column on the 1989-2022 slice, but only 162 columns were probed.** If a new V3b-only column had been inadvertently added (it wasn't — column count is identical 73/89 across baseline and new parquet), the slice-comparison would miss it. Mitigation: column count parity is explicit (73 harm cols + 89 derived cols; matches pre-V3b state).

2. **The B3 1-digit recode for V3b code 7 → null is the same convention as V3a's 09 → null, but if NCHS has a documented bridged-race convention specifically for 1978-revision code 7 that I missed, my null mapping may diverge from that.** Same residual as V3a (DECISION_LOG 2026-05-12T14:30:00Z item a); search of NVSR Series 21 reports for 1982-1988 race-stratified fetal death tables is post-submission scope.

3. **The DATAYEAR expansion is hard-coded "19" + 2-digit raw.** If any V3b zip somehow contained Y2K-rollover records (which the 1978-revision predates), the expansion would produce "1900" or similar. Mitigation: `_era_tag` bounds V3b to 1982-1988; no risk in practice.

4. **The 7 V3b user-guide control counts were transcribed from the page-7 "By residence" cells.** If a transcription error landed (e.g., a digit swap), the validator would FAIL — but it didn't, 33/33 PASS. So either the controls are correct OR the parser also has a matching error that cancels out. The probability of a coincidental parser-vs-doc cancellation is negligible (would need to bias each year independently by the exact transcribed digit).

5. **Schema CSV `years_available` extension was conservative (prepend only).** For V3b-covered rows, V3a's deferred 1989-1991 gap remains in the years_available string ("1982-1988, 1992-2002, ..." rather than "1982-2022"). Documented in V3b_LAYOUT_DECISIONS.md "What V3b does NOT do" section. Downstream code uses `data_year` directly, not the schema string, so this is doc-only drift — fix-on-contact at Task 10 (Zenodo polish).

6. **The 1985 OCR ambiguity `29,66I` → `29,661` was resolved empirically by canonical-filter cross-check, not by visual OCR repair.** The empirical resolution is the authoritative answer (the byte-exact parser→filter→count chain must agree with the published control), but if NCHS's actual control was something else (say `29,664` mis-displayed in the PDF), our parser would over-count by some amount. Mitigation: the value `29,661` is consistent with the 1984 (30,099) → 1986 (28,972) inter-annual trend.

7. **V3b's NUMDEL → plurality direct mapping conflates V3b code 3 (Triplet+) with V1 code 3 (Triplet exactly).** ~107 records/yr have plurality=3 in V3b vs the disambiguated 3/4/5 in V1. For multi-year plurality time-series, the 1988→1989 boundary will show a small artifactual blip in code-3 counts (V3b "3+" vs V3a "3"). Documented in V3b_LAYOUT_DECISIONS.md. Not caught by VERIFY because the V3b user-guide controls are unstratified by plurality.
